# ชื่อเรียกรถ

เพิ่ม `vehicles.nickname` สำหรับชื่อหรือรหัสเรียกรถ เช่น `32-002-BFn` คู่กับทะเบียน `16-5728` ชื่อเรียกไม่เกิน 100 ตัวอักษร เว้นว่างได้ และซ้ำกันได้เมื่อรถมีทะเบียน ระบบยังผูกประวัติและงานกับรหัสรถเดิม

ตั้งแต่ migration 017 รถมีชื่อเรียกอย่างเดียวโดยไม่มีทะเบียนได้ ดูรายละเอียดกฎและขั้นตอนนำขึ้นใช้งานใน `docs/vehicle-plate-or-nickname-plan.md`

แอดมินเพิ่มหรือแก้ชื่อได้ที่ **จัดการรถ → เพิ่มรถ / แก้ไข** รวมถึงหน้าจัดการรถของ super admin ช่างใส่ชื่อได้ตอนเพิ่มรถใหม่ในหน้าถอด–ใส่ยาง รถเดิมยังไม่ถูกกำหนดชื่ออัตโนมัติจากภาพตัวอย่าง

ค้นหาชื่อบางส่วนได้ เช่น `bfn` หรือ `SG+` โดยไม่สนตัวพิมพ์เล็ก–ใหญ่ ในรายการรถ หน้าถอด–ใส่ยาง และหน้าบันทึกเลขไมล์ ผลค้นหาแสดงทะเบียนกับจังหวัดและเลือกด้วย UUID เพื่อรองรับชื่อซ้ำ ส่วนคลังยางค้นได้จากชื่อรถที่ติดตั้งอยู่หรือรถที่ถอดออกครั้งล่าสุด

ชื่อเรียกแสดงร่วมกับทะเบียนในรายละเอียดรถ ประวัติยาง รายงาน การแจ้งเตือน และการส่งออก รายการรถใน Excel มีคอลัมน์ชื่อเรียกแยกจากทะเบียน

## นำขึ้นใช้งาน

1. ฐานข้อมูลเดิม: รัน `supabase/migrations/016_vehicle_nickname.sql` หลัง migration 015 และก่อนนำโค้ดนี้ขึ้นใช้งาน ไฟล์ทำงานใน transaction และรันซ้ำได้
2. ตรวจด้วย `supabase/scripts/verify_016.sql` ซึ่งอ่านข้อมูลอย่างเดียว
3. Deploy แอป แล้วเพิ่มชื่อจริงให้รถผ่านฟอร์มแก้ไข
4. ฐานข้อมูลใหม่ใช้ `supabase/schema.sql` ที่ปรับแล้วได้ตามขั้นตอนเดิม

Migration ต่อท้ายคอลัมน์ใน views และคง `security_invoker=true` ไม่แก้ทะเบียน เลขไมล์ ประวัติยาง หรือสูตรคำนวณระยะเดิม

### ผลต่อระบบที่กำลังใช้งาน

เป็นการเพิ่มคอลัมน์ที่ยอมให้ว่างได้ จึงออกแบบให้แอปเวอร์ชันเดิมใช้ข้อมูลเดิมต่อได้ และค่อยนำแอปเวอร์ชันใหม่ขึ้นหลัง migration สำเร็จ รถเดิมต้องกรอกชื่อจริงภายหลัง

ไฟล์นี้ไม่ได้รับประกัน zero downtime: `ALTER TABLE` ล็อกตารางรถ และสร้างดัชนีแบบปกติภายใน transaction เดียวกัน จึงอาจทำให้การอ่านหรือบันทึกที่เกี่ยวข้องกับรถรอจน commit ระยะเวลาขึ้นกับจำนวนรถและ transaction ที่กำลังทำงานอยู่ ซึ่งยังไม่ได้ตรวจบน production ไม่ควรสรุประยะเวลาจากฐานทดสอบขนาดเล็ก

ก่อนรันจริงให้ตรวจว่าฐานข้อมูลถึง migration 015 และไม่มีการแก้ views นอกโค้ดที่ต้องรักษาไว้ ตรวจความพร้อมของ backup แล้วรันช่วงที่หยุดบันทึกงานได้ หลัง migration ตรวจด้วย `verify_016.sql` ก่อน deploy ถ้าคำสั่งใน transaction ล้มเหลว ให้ rollback transaction นั้น การเปลี่ยนแปลงของ migration จะไม่ถูก commit บางส่วน

หากต้องเปิดใช้งานต่อเนื่องระหว่างเปลี่ยนฐานข้อมูล ควรจัดลำดับใหม่ให้การสร้างดัชนีแบบ `CONCURRENTLY` อยู่นอก transaction ที่แก้ schema และกำหนด lock timeout ก่อนใช้งานจริง ทั้งนี้การเปลี่ยน schema ยังต้องขอล็อกตารางอยู่

## ตรวจรับ

- เพิ่มชื่อ `32-002-BFn` ให้รถ แล้วค้น `bfn` ในรายการรถและหน้าช่าง ต้องเจอทะเบียนที่ถูกต้อง
- ทดสอบ `588-233-SG+`, ชื่อภาษาไทย และรถที่ยังไม่มีชื่อ
- ตั้งชื่อซ้ำให้รถสองคัน ตรวจว่าระบบแสดงทั้งสองคันพร้อมทะเบียนและจังหวัด เลือกคันหนึ่งแล้วตรวจว่าหน้าถัดไปและรายการที่บันทึกเป็นคันนั้น
- ค้นทะเบียนเดียวกันต่างจังหวัดแล้วเลือกจากผลค้นหา ต้องไม่เลือกรถคันแรกให้อัตโนมัติ
- แก้ชื่อและล้างชื่อกลับเป็นค่าว่างได้ ประวัติถอด–ใส่ยางยังอยู่กับรถคันเดิม
- ตรวจชื่อในคลังยาง ประวัติ รายงาน และ Excel/PDF รวมถึงตรวจว่าบริษัทอื่นมองไม่เห็นรถของบริษัทนี้

ทดสอบตรรกะการค้นหาและตรวจค่า: `node --experimental-strip-types --test scripts/vehicle-nickname.test.mjs` (Node 22.6+)

ตรวจโค้ด: `npx tsc --noEmit`, `npm run lint`, `npm run build -- --webpack`

การตรวจระหว่างพัฒนา: ชุดทดสอบ 6 กรณีผ่าน, TypeScript ผ่าน, lint ไม่มี error (มี warning เดิม 7 จุด), build ด้วย Webpack ผ่าน และทดสอบ fresh schema / migration ซ้ำสองครั้งบน PostgreSQL 16 ชั่วคราวผ่าน รวมถึงการคงข้อมูลเดิม ชื่อซ้ำ การค้นหา และ RLS ของบริษัท ยังไม่ได้ apply บนฐานข้อมูลจริงหรือทดสอบ UI ผ่าน Browser เนื่องจากเซสชันนี้ไม่มีเครื่องมือเรียก Browser
